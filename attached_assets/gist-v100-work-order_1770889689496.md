## Phase 1: Security

*A real user means real attack surface. These are non-negotiable before handing out a link.*

### 1.1 Rate Limiting on OTP Endpoints

There is NO rate limiting on any OTP endpoint. An attacker can spam OTP requests and burn through the Resend email quota.

**Install `express-rate-limit`:**

```bash
npm install express-rate-limit
```

**Add to `server/index.ts` or `server/routes.ts`:**

```typescript
import rateLimit from "express-rate-limit";

const otpLimiter = rateLimit({
  windowMs: 15 * 60 * 1000, // 15 minutes
  max: 5, // 5 requests per window per IP
  standardHeaders: true,
  legacyHeaders: false,
  message: { message: "Too many requests. Try again in a few minutes." },
});
```

**Apply to these four routes:**

```typescript
app.post("/api/auth/request-otp", otpLimiter, async (req, res) => { ... });
app.post("/api/auth/verify-otp", otpLimiter, async (req, res) => { ... });
app.post("/api/g/:slug/verify", otpLimiter, async (req, res) => { ... });
app.post("/api/g/:slug/verify/confirm", otpLimiter, async (req, res) => { ... });
```

### 1.2 OTP Attempt Enforcement

The constant `OTP_MAX_ATTEMPTS = 3` is defined on line 10 of `routes.ts`, and `storage.incrementOtpAttempts()` is called — but the code does not check the attempts count before accepting a verification. Fix:

In the OTP verification handlers (both author and contributor), BEFORE checking if the code matches, verify:

```typescript
if (otp.attempts >= OTP_MAX_ATTEMPTS) {
  return res.status(429).json({ message: "Too many attempts. Request a new code." });
}
```

**Test by:**
- Request an OTP
- Enter wrong code 3 times
- 4th attempt should return 429, not check the code
- Request a new OTP → fresh 3 attempts

## Phase 2: Architectural Integrity

*These close gaps where the product breaks its own core promises.*

### 2.1 Timeline Entries Written to .md Source

Currently timeline entries are DB-only. The PRD says "the .md file is the canonical artifact." An exported .md has no timeline — that breaks the promise.

When a timeline entry is created (auto or manual), append a blockquote primitive to the gist's `markdownSource`:

```typescript
// After creating the timeline entry in DB, also update the markdown
const timelineBlock = `\n\n> **Timeline:**\n> - ${new Date().toISOString().split("T")[0]} · ${description}\n`;

// Append to existing timeline block if one exists, or add new one
const existingTimeline = gist.markdownSource.match(/> \*\*Timeline:\*\*\n(> - .+\n)*/);
if (existingTimeline) {
  // Insert new entry at the top of the existing timeline block (reverse-chronological)
  const newEntry = `> - ${date} · ${description}\n`;
  const updatedSource = gist.markdownSource.replace(
    /> \*\*Timeline:\*\*\n/,
    `> **Timeline:**\n${newEntry}`
  );
  await storage.updateGist(slug, authorId, { markdownSource: updatedSource });
} else {
  // Append a new timeline block at the end
  const updatedSource = gist.markdownSource + timelineBlock;
  await storage.updateGist(slug, authorId, { markdownSource: updatedSource });
}
```

Apply this to EVERY place `storage.createTimelineEntry()` is called in `routes.ts` (lines ~204, ~243, ~382, ~443, ~490).

**Test by:**
- Create a gist, add a thread, add a decision
- Export the .md
- Open in VS Code → verify timeline blockquote is present with entries

### 2.2 Frontmatter Stripped from CodeMirror

The title bar works, but CodeMirror still receives the full markdown including `---` fences. Users can see and accidentally edit the frontmatter.

**In `editor.tsx`, strip frontmatter before passing to GistEditor:**

```typescript
// When loading gist content, strip frontmatter for the editor
const bodyContent = useMemo(() => {
  return markdown.replace(/^---\n[\s\S]*?\n---\n*/, "");
}, [markdown]);

// Pass bodyContent to GistEditor instead of markdown
<GistEditor
  value={bodyContent}
  onChange={(val) => {
    // Store the body content, reconstruct full markdown on save
    setBodyMarkdown(val);
    setHasChanges(true);
    scheduleAutoSave();
  }}
  // ...
/>
```

**On save, reconstruct full markdown:**

```typescript
const fullMarkdown = `---\ntitle: ${title}\nupdated: ${new Date().toISOString().split("T")[0]}\n---\n\n${bodyMarkdown}`;
```

The key insight: maintain TWO pieces of state — `title` (from frontmatter) and `bodyMarkdown` (everything after). Reconstruct on save.

**Do NOT** change the stored format, export format, or API contract. Just change what the editor surface shows.

### 2.3 Access Control UI

The author cannot change the access tier. "Anyone with link" is a static label. The backend already supports `accessTier` updates — this is purely a frontend gap.

**In `share-link.tsx`, replace the static label with a dropdown:**

```tsx
import { Select, SelectContent, SelectItem, SelectTrigger, SelectValue } from "@/components/ui/select";

// Replace static span with:
<Select
  value={accessTier}
  onValueChange={(value) => onAccessTierChange(value as "open" | "verified" | "restricted")}
>
  <SelectTrigger className="h-7 text-[12px] font-mono border-0 bg-transparent w-auto gap-1.5">
    <SelectValue />
  </SelectTrigger>
  <SelectContent>
    <SelectItem value="open">Anyone with link</SelectItem>
    <SelectItem value="verified">Email verified</SelectItem>
    <SelectItem value="restricted">Restricted access</SelectItem>
  </SelectContent>
</Select>
```

**In `editor.tsx`, wire up the callback:**

```typescript
const updateAccessTier = useMutation({
  mutationFn: async (tier: string) => {
    await apiRequest("PUT", `/api/gists/${slug}`, { accessTier: tier });
  },
  onSuccess: () => {
    queryClient.invalidateQueries({ queryKey: ["/api/gists", slug] });
  },
});

// Pass to ShareLink:
<ShareLink
  slug={slug}
  accessTier={gist?.accessTier}
  onAccessTierChange={(tier) => updateAccessTier.mutate(tier)}
/>
```

**For "restricted" tier:** when selected, show an additional input for the allow-list (comma-separated emails/domains). Save via the same `PUT /api/gists/:slug` endpoint which already accepts `allowList`.

**Test by:**
- Create a gist
- Click the access tier dropdown → change to "Email verified"
- Open viewer in incognito → should require email OTP to view
- Change to "Restricted" → add an allow-list email
- Try accessing with a different email → should see "You don't have access"
