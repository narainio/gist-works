## 1. Problem Statement

Cross-org knowledge workers — fractional execs, senior freelancers, distributed teams with external stakeholders — cannot build shared context with the people they collaborate with. People come from different starting points, learn and inform themselves in different ways, and all of this is happening while they're simultaneously trying to collaborate.

Their work artifacts are scattered across platforms they don't control: decisions live in Slack threads, context lives in meeting recordings, documents live in whatever Google Workspace or Notion instance the client happens to use. Nothing is authoritative. When a client engagement ends, the worker loses access to the client's tools — and their own knowledge and decisions disappear into someone else's platform.

The fragmentation drives tool sprawl and cognitive overhead: 8.8 apps daily average, ~1,200 context switches/day, up to 40% of productive time lost to reorientation. Two to three active clients is the burnout ceiling — not because of the work itself, but because of the tooling overhead.

Shared context is the "screen sharing" of productivity tools — every product has some version of it and it's always a shitty add-on. Slack has threads that die. Google Docs has comments nobody reads. Notion has databases that silo. Meeting tools have transcripts that disconnect. Everyone does "context" and everyone does it badly — because for all of them, context is a feature, not the product.

**Evidence:**
- 8.8 apps daily, ~1,200 context switches/day, 40% productive time lost (HBR, Asana, Salesforce studies) — Strong
- 1.57B freelancers globally, fractional exec LinkedIn profiles up 5,400% 2022-2024 — Strong
- No existing tool at the intersection: shared context + zero identity tax + local-first + ambient + AI-native + cross-org — Strong
- ADRs validate canonical artifacts in engineering; Coda partially validates doc-as-collaboration-surface — Strong
- Local-first/CRDT infrastructure production-ready (Yjs, Automerge 2.0, TinyBase, Tuple) — Strong

## 3. Target User

**Primary:** People who work across multiple organizations simultaneously and don't control the stack in any of them. Fractional CTOs, senior product consultants, advisory-level freelancers, and small distributed teams that include external collaborators (contractors, advisors, fractional execs).

**Behavioral definition:**
- Toggle between sync and async constantly
- Maintain 2-5 concurrent clients or projects
- Have built personal workarounds they know are inadequate
- When a client engagement ends, they lose access to the client's tools and their own work disappears
- Often "out ahead" of the people they collaborate with — they see things others don't see yet, they've done the work to get there, but shared context hasn't been built
- Currently solve the "bringing people along" problem manually: re-explaining context in every meeting, copy-pasting decisions into personal notes, maintaining shadow docs, re-creating context from memory

**Secondary:** The collaborators of the primary user — clients, stakeholders, team members who receive a shared Gist link. They are not the buyer or the creator, but their experience (the collaborator aha) is the product's primary value demonstration.

## 4. Scope

### In Scope (MVP)

1. **Gist creation and editing** — web-based editor for creating and editing Markdown artifacts with the six-primitive stack
2. **Four of six primitives** — Document (.md spine), Decisions, Threads (native only), Timeline
3. **AI synthesis** — context synthesis engine that generates views, distills content, maintains timelines
4. **Sharing with zero identity tax** — link-based access following DropLeaf's model
5. **Contributor identity** — email OTP + display name for thread contributions
6. **Author accounts** — email OTP, persistent session, multi-Gist management
7. **Email thread ingestion** — product-as-participant email address for ingesting email threads
8. **Design system implementation** — full Warm Signal design system as defined in `design-system.md`
9. **Business model infrastructure** — 1 free Gist, paid tier for unlimited (pricing TBD)
10. **BYOK OpenRouter integration** — bring your own key, with bundled free tokens for cold start

### Out of Scope (MVP)

| Item | Why excluded | When it might return |
|------|-------------|---------------------|
| Snapshots primitive | Requires non-text capture mechanism not yet designed | V2 — after core stack validates |
| Views primitive (stored) | AI-generated views are computed on-demand, not stored as primitives in the .md | Revisit if performance requires caching |
| Slack/WhatsApp/Teams integration | Each is a meaningful integration effort | V2 — prioritized by user demand |
| Google Docs integration | Identity tax tension (requires Google account) | V2 — if demand validates |
| Video call transcription ingestion | Don't build the transcriber, ingest from others | V2 |
| Desktop folder sync | Native desktop integration | V2 — keeps file-over-app alive |
| CRDT-based real-time co-editing | Infrastructure exists but adds complexity to MVP | V2 — after single-author + async contribution validates |
| Native mobile app | Responsive web covers mobile | Only if responsive proves insufficient |
| Enterprise features (SSO, audit, compliance) | Not target user | Only if market pulls toward enterprise |
| Customization/theming | Opinionated defaults | Likely never |

### Scope Rationale

**Why 4 of 6 primitives, not all 6:** Snapshots require a non-text capture mechanism (browser extension, API integration, or manual upload flow) that adds scope without validating the core thesis. Views are computed by AI on-demand — they don't need to be stored as primitives in the .md. The four included primitives (Document, Decisions, Threads, Timeline) are sufficient to test both uncertain assumptions: (1) shared context adoption and (2) AI quality as connective tissue.

**Why no real-time co-editing:** The primary interaction model is author-creates, collaborator-contributes-async (via threads). Real-time co-editing is a V2 feature if async collaboration validates first. This dramatically reduces infrastructure complexity for MVP.

**Why email first for integration:** Universal (everyone has email), no API dependency, no accounts required, behavior pattern already understood (CC someone). Validates the product-as-participant model before investing in platform-specific integrations.

## 5. Solution Overview

**Gist** is a web application that creates shared context surfaces. The atomic unit is a Gist — a Markdown file with structured primitives that serves as the canonical collaboration surface, decision record, and deliverable in one object.

### Core Architecture

```
┌─────────────────────────────────────────────────┐
│                   WEB APP                        │
│                                                  │
│  ┌───────────┐  ┌───────────┐  ┌──────────────┐ │
│  │  Editor   │  │  Viewer   │  │  Synthesis   │ │
│  │  (Author) │  │  (Collab) │  │  Panel       │ │
│  └─────┬─────┘  └─────┬─────┘  └──────┬───────┘ │
│        │              │               │          │
│  ┌─────┴──────────────┴───────────────┴───────┐  │
│  │         Rendering Engine                    │  │
│  │  (Parses .md → design system components)   │  │
│  └─────────────────┬──────────────────────────┘  │
│                    │                             │
│  ┌─────────────────┴──────────────────────────┐  │
│  │         Gist Data Layer                     │  │
│  │  (Markdown storage, primitive parsing,      │  │
│  │   frontmatter management, contributor       │  │
│  │   sessions)                                 │  │
│  └─────────────────┬──────────────────────────┘  │
│                    │                             │
│  ┌────────┐  ┌─────┴────┐  ┌──────────────────┐ │
│  │ Auth   │  │ Storage  │  │ AI Synthesis     │ │
│  │ (OTP)  │  │ (DB +    │  │ (OpenRouter API) │ │
│  │        │  │  files)  │  │                  │ │
│  └────────┘  └──────────┘  └──────────────────┘ │
│                                                  │
│  ┌──────────────────────────────────────────────┐│
│  │         Email Ingestion Service              ││
│  │  (Receives email, parses threads,            ││
│  │   distills via AI, updates Gist)             ││
│  └──────────────────────────────────────────────┘│
└─────────────────────────────────────────────────┘
```

### The Two Faces

**Author experience:** Create Gists, edit the .md spine, add primitives (decisions, threads, timeline entries), invoke AI synthesis, share links, manage multiple Gists. Requires email OTP account.

**Collaborator experience:** Open a shared link (no account), see the AI-generated synthesis view as the entry point, drill into primitives (decisions, threads, timeline), contribute to threads (email OTP + display name). Zero identity tax.

### Primitive Stack (MVP — 4 of 6)

**Document** — The canonical .md spine. Authored in Markdown. Contains body text and all other primitives as blockquote-convention blocks. Frontmatter holds artifact-level metadata (title, created, updated, contributors).

**Decision** — Structured block: question → options → evidence → conclusion → rationale → participants → date. Rendered with `primitive-decision` left border (#0D7C66). Collapsible. Represents a choice that was made, with full context for why.

**Thread** — Discussion block: messages from contributors with source indicator. Native threads are authored in-product. Email threads are ingested and AI-distilled (key messages + summary, not full transcript). Rendered with `primitive-thread` left border (#8A8680). Shows contributor names, source (native/email), message count.

**Timeline** — Auto-generated reverse-chronological log of meaningful events: decisions made, threads started, document edits, contributors added. Author can add manual entries. Rendered with `primitive-timeline` left border (#C4B5A0). Dates in monospace. Entries expandable.

### AI Synthesis

The core technical primitive. AI reads the entire Gist (all primitives) and generates:

1. **Synthesis view** — The front door for collaborators. An AI-generated summary answering: "Here's where things stand, here's what was decided, here's what's open." Displayed in the Synthesis Panel component.
2. **View types** — Selectable projections: Executive Summary, Full Context, Decisions Only, What Changed (since last visit).
3. **Thread distillation** — When an email thread is ingested (or a long native thread accumulates), AI distills it to key messages + summary for the .md representation.
4. **Timeline generation** — AI maintains the timeline from raw history, creating meaningful entries (not just "file edited at 3:42pm" but "Decision made: US East Coast launch market").

AI is invoked via OpenRouter. Model selection is user-configurable. Bundled free tokens for cold start. BYOK tutorial in onboarding (skippable, re-triggerable).

### Email Ingestion

Each Gist can have a dedicated email address (e.g., `{gist-slug}@gist.works`). When this address is CC'd on an email thread:

1. Incoming email is received by the ingestion service
2. Email is parsed: sender, recipients, subject, body, thread ID
3. AI distills the thread into key messages + summary
4. A Thread primitive is added to the Gist with source indicator "Email"
5. Timeline is updated: "Thread ingested: [subject] (Email)"

The author adds/removes the email address from threads like adding/removing a person.

### Sharing Model

Based on DropLeaf's architecture. Each Gist has a shareable URL: `gist.works/g/{slug}` (10-character nanoid).

| Access Level | Gate | Identity | Capabilities |
|-------------|------|----------|-------------|
| View | None (open link) | None | Read synthesis, read all primitives, browse timeline |
| Contribute | Email OTP + display name | Transient (24h cookie) | Everything in View + add to native threads |
| Restricted | Email OTP + allow-list | Transient (24h cookie) | Same as Contribute, but only allowed emails/domains can access |
| Author | Email OTP account | Persistent session | Full edit, create/delete primitives, invoke synthesis, manage sharing, manage email ingestion |

### Data Model

Gists are stored as Markdown with YAML frontmatter and blockquote-convention primitives. See `pre-prd-definitions.md` for the full schema specification. The .md source is the canonical representation. The rendered view (with design system styling) is computed from the .md source at display time.

**Database stores:**
- Gist metadata (id, slug, author, created, updated, access tier, allow-list)
- Author accounts (id, email, session tokens)
- Contributor sessions (per-Gist, email, display name, session token, expiry)
- OTP records (ephemeral, 10-minute expiry, 3-attempt limit)
- Email ingestion configuration (Gist → email address mapping)
- AI token usage tracking (bundled allocation + BYOK flag)

**The .md source itself is stored in the database** (not as a file on disk), similar to DropLeaf. The file-over-app principle is honored through export: any Gist can be downloaded as a .md file that's readable in any Markdown editor.

## 6. User Scenarios

### 6.1 Happy Path — Author Creates and Shares a Gist

**Precondition:** Author has an account (email OTP).

1. Author clicks "New Gist"
2. A blank Gist opens with a title field and an empty .md body
3. Author types a title: "Project Alpha — Q1 Strategy"
4. Author writes body text in Markdown
5. Author adds a Decision primitive: clicks "Add Decision," fills in question, options, evidence, conclusion, rationale
6. The Decision appears as a blockquote block in the editor with the `primitive-decision` left border
7. Author clicks "Synthesize" — AI generates a synthesis view
8. The Synthesis Panel appears at the top showing an executive summary of the Gist
9. Author clicks "Share" — a link is generated (`gist.works/g/a1b2c3d4e5`)
10. Author copies the link and sends it to a collaborator via email/Slack/etc.
11. Timeline auto-updates: "Gist created," "Decision added: [question]," "Synthesis generated," "Link shared"

### 6.2 Happy Path — Collaborator Gets the Gist

**Precondition:** Collaborator has received a link. No account, no install.

1. Collaborator clicks the link: `gist.works/g/a1b2c3d4e5`
2. The page loads. The **Synthesis Panel is the first thing they see** — an AI-generated summary of where things stand
3. Below the synthesis, the full Gist renders with all primitives (document body, decisions with left borders, threads, timeline)
4. Collaborator reads the synthesis and scans the decision blocks by their teal left border
5. They expand a Decision to read the full rationale
6. They want to ask a question — they click "Add to Thread" on a specific section
7. A prompt asks for their email and display name
8. They enter both, receive an OTP, verify
9. They type their question in the native thread
10. The thread appears in the Gist with their display name
11. Timeline auto-updates: "New contributor: [name]," "Thread message added"

### 6.3 Happy Path — Email Thread Ingestion

**Precondition:** Author has enabled email ingestion for the Gist.

1. Author is in an email conversation with a client about launch strategy
2. Author CCs `project-alpha@gist.works` on the email thread
3. The email ingestion service receives the email
4. AI distills the email thread: extracts key messages, summarizes, identifies participants
5. A Thread primitive is added to the Gist: "Email · project-alpha thread · [date]"
6. The distilled thread shows key messages attributed to senders, with a summary line
7. Timeline updates: "Thread ingested: project-alpha (Email) · 3 messages · 2 participants"
8. Next time someone opens the Gist, the synthesis view includes the email thread context

### 6.4 Error States

| Scenario | Expected Behavior |
|----------|------------------|
| **OTP expired (10 min)** | "Your code has expired. Request a new one." Re-send OTP. |
| **OTP wrong 3 times** | "Too many attempts. Request a new code." Invalidate current OTP, allow re-request. |
| **Restricted Gist, email not on allow-list** | "You don't have access to this Gist. Contact the author if you think this is a mistake." No content shown. |
| **AI synthesis fails (OpenRouter error)** | "Synthesis unavailable right now. You can still read the full Gist below." Show the raw Gist without synthesis panel. Never block access to content because of AI failure. |
| **AI synthesis slow (>5s)** | Show Synthesis Panel immediately with canvas background. Populate content as it streams in. No spinner, no skeleton. Content area is present at full height, text appears progressively. |
| **Email ingestion receives spam/irrelevant email** | AI classifies as irrelevant. Email is discarded. No Thread primitive created. Author can view a log of discarded emails. |
| **Email ingestion receives email not from a thread** | Treat as a single-message thread. AI distills normally. |
| **Author's bundled tokens exhausted, no BYOK key** | "You've used your included tokens. Add your OpenRouter key to keep synthesizing." Link to the BYOK tutorial (re-triggerable). Gist is still fully readable and editable — only synthesis is paused. |
| **Invalid or rate-limited OpenRouter key** | "There's an issue with your API key. Check your OpenRouter dashboard." Never expose the raw API error. |
| **Gist not found (invalid slug)** | "This Gist doesn't exist or has been removed." Clean 404. |
| **Author loses session (cookie cleared)** | Author can re-authenticate via email OTP to reclaim their account and all Gists. |

### 6.5 Edge Cases

| Scenario | Expected Behavior |
|----------|------------------|
| **Same email contributes to multiple Gists** | Each Gist has a separate contributor session. No cross-Gist identity linking. |
| **Author shares a Gist then deletes it** | Soft delete. Existing links show: "This Gist has been removed by its author." No content. |
| **Very long Gist (50+ primitives)** | Primitives are collapsible. Synthesis view remains the entry point. Performance must not degrade — paginate or lazy-load primitives if needed. |
| **Email thread in non-English language** | AI handles multilingual content. Thread is distilled in the language of the email. |
| **Multiple email threads ingested to same Gist** | Each becomes a separate Thread primitive with its own source/date. Timeline shows each. Synthesis incorporates all. |
| **Collaborator tries to contribute to a Gist with View-only access tier** | Contribute affordances (thread reply buttons) are hidden. Only View is available. |
| **Author has 1 free Gist, creates a second** | Paywall: "You've reached your free Gist limit. Upgrade to create more." The existing Gist remains fully functional. |
| **Author downgrades from paid to free with 5 active Gists** | All 5 remain accessible and functional. Author cannot create new Gists until they're at 1 or re-upgrade. No deletion of existing Gists. |
| **Gist .md downloaded and opened in VS Code** | All primitives render as blockquotes with typed prefixes (> **Decision:**, > **Thread:**, > **Timeline:**). Frontmatter shows as YAML. Fully readable. |

## 7. Architecture & Technical Considerations

### Tech Stack Constraints

| Layer | Constraint | Rationale |
|-------|-----------|-----------|
| Frontend | Web app, single-page application | Two-face model (author + collaborator) on same rendering engine |
| Backend | Server-side API (Node.js/Express recommended, based on DropLeaf precedent) | Reuse DropLeaf's patterns for auth, OTP, session management |
| Database | PostgreSQL (based on DropLeaf precedent) | Gist metadata, auth, sessions, OTP, email config |
| AI | OpenRouter API | Model-agnostic, BYOK, routing/fallbacks handled by OpenRouter |
| Email | Inbound email parsing service (e.g., Mailgun, SendGrid Inbound Parse, or Cloudflare Email Workers) + Resend for outbound OTP | Email ingestion for thread capture; OTP delivery |
| Markdown | `marked.js` for parsing (DropLeaf precedent) + custom primitive parser | Standard Markdown rendering + blockquote-convention primitive detection |
| Hosting | Cloud hosting with HTTPS | Standard web app deployment |

### Key Technical Decisions

**Markdown as source of truth:** The .md content (with frontmatter and blockquote-convention primitives) is the canonical representation. The database stores the raw .md source. The rendered view is computed at display time by parsing the .md and applying the design system. This means:
- Export is trivial (download the stored .md)
- Graceful degradation is guaranteed (the .md IS the fallback)
- The rendering engine must parse blockquote prefixes (> **Decision:**, > **Thread:**, > **Timeline:**) and render them with the appropriate design system components

**Primitive parser specification:** The rendering engine must detect and parse these blockquote patterns:

```
> **Decision:** {question}
> - **Options:** {option1} | {option2} | ...
> - **Evidence:** {text}
> - **Conclusion:** {chosen option}
> - **Rationale:** {text}
> - **Decided:** {date} · {participants}
```

```
> **Thread:** {source} · {date}
> - **{Name}:** {message}
> - **{Name}:** {message}
> - {count} messages · {count} participants
```

```
> **Timeline:**
> - {date} · {event description}
> - {date} · {event description}
```

Each detected primitive block is rendered using its corresponding design system component (left border, label, collapse/expand, etc.) instead of as a plain blockquote.

**AI synthesis is stateless:** The synthesis is computed each time it's requested. The AI receives the full .md content and generates the view. There is no stored synthesis — it's always fresh. This simplifies the data model but means synthesis latency matters (must be <5s).

**No real-time sync in MVP:** Authors edit; collaborators contribute asynchronously via threads. There is no simultaneous editing. This eliminates the need for CRDTs, operational transforms, or WebSocket infrastructure in MVP. The database is the synchronization point — author writes, contributors read + add threads.

### Dependencies

| Dependency | Type | Risk |
|-----------|------|------|
| OpenRouter API | External service | Medium — if OpenRouter is down, synthesis fails. Mitigation: graceful degradation (Gist still readable without synthesis). |
| Inbound email service | External service | Medium — if email parsing fails, thread ingestion fails. Mitigation: email retry queue. |
| Resend (outbound email) | External service | Low — if Resend is down, OTP delivery fails. Mitigation: rate-limited retries. |
| PostgreSQL | Infrastructure | Low — standard, mature, well-understood. |

### Performance Requirements

| Operation | Target | Rationale |
|----------|--------|-----------|
| Page load (Gist view) | <1.5s to first contentful paint | Collaborator's first impression |
| Synthesis generation | <5s to first token, streaming thereafter | Core technical primitive — slow = broken trust |
| Primitive collapse/expand | <100ms | Snap motion per design system |
| OTP delivery | <30s | Standard email delivery expectation |
| Email ingestion (receipt to Gist update) | <60s | Near-real-time thread capture |

## 8. Design Constraints

**Authoritative document:** `design-system.md` (Version 1.0, 2026-02-11)

The build agent MUST read `design-system.md` in full before implementing any UI. Key constraints that affect requirements:

### Non-Negotiable Design Rules

1. **Primitive blocks use 3px left borders** in their assigned colors: Decision (#0D7C66 light / #2EAA8E dark), Thread (#8A8680 / #6B6965), Timeline (#C4B5A0 / #8A7E6E). These borders are how users scan and identify primitive types.

2. **Accent color (#0D7C66) is interactive.** If it's accent-colored, it must be clickable or signal a structured decision. Never decorative.

3. **Content width max 680px.** Body text, primitives, and synthesis all render within this width. Sidebar (navigation, meta) is secondary, max 280px.

4. **Typography:** Inter for UI/content, JetBrains Mono for timestamps/metadata/code. Both loaded locally, not from CDN.

5. **Motion: snap, don't slide.** 100ms for micro interactions, 150ms for layout transitions. ease-out. No bounce, no spring, no overshoot.

6. **Dark mode: automatic via OS preference.** No manual toggle in V1. Warm canvas (#1C1917), not pure black.

7. **No skeleton screens, no spinners, no shimmer.** Content areas appear immediately at full height. Content populates without layout shift.

8. **Surface colors are always warm.** Never pure #FFFFFF (light) or #000000 (dark).

9. **Primitive labels** (DECISION, THREAD, TIMELINE) are always uppercase, 11px, weight 600, 0.05em letter-spacing.

10. **Minimum touch target: 44px × 44px** for all interactive elements.

### Graceful Degradation (Design Implications)

When a Gist is exported as .md and opened in any Markdown renderer:
- Decisions → blockquotes with "**Decision:**" prefix
- Threads → blockquotes with "**Thread:**" prefix and contributor names
- Timeline → blockquote with ordered list and dates
- All content is readable. No information is lost.

Test every design decision against: "Does this work as plain Markdown?"

## 10. Risks & Mitigations

| # | Risk | Likelihood | Impact | Mitigation |
|---|------|-----------|--------|-----------|
| R1 | **AI quality ceiling** — synthesis is mediocre, not "instant, accurate, genuinely useful" | Medium | Critical | This is the coupled assumption (#1 + #3). Mitigation: extensive prompt engineering during build. Model-agnostic via OpenRouter lets us switch models. Fallback: Gist still works as a well-structured .md — just less differentiated. |
| R2 | **Anthropic platform risk** — Claude/Cowork builds this capability natively | Low | High | Platform-vs-product distinction. Anthropic builds infrastructure; Gist is an opinionated product ON that infrastructure. The difficulty of copying coherent opinion (Linear/Jira pattern) is the defense. Monitor Anthropic roadmap. |
| R3 | **Email ingestion reliability** — spam, malformed emails, thread detection failures | Medium | Medium | AI classification of relevance. Discarded email log for author review. Thread detection heuristics (In-Reply-To, References headers). Graceful failure: bad emails are ignored, never corrupt the Gist. |
| R4 | **Adoption paradox** — even an ambient tool adds to the landscape | Medium | High | File-over-app: the .md works without the tool. Bring-your-own-threads: the product integrates with existing communication, doesn't replace it. First-use experience must be frictionless — golden path to aha in <5 minutes. |
| R5 | **BYOK friction** — users bounce at "paste your API key" | Low (bundled tokens mitigate) | Medium | Bundled free tokens eliminate cold-start friction. Tutorial is optional and re-triggerable. The "pay with your own key" message comes after value is proven, not before. |
| R6 | **Scope creep via primitives** — 4 primitives is ambitious for MVP | Medium | Medium | Sequencing: Document + Decisions first (core value), then Threads + Timeline. If build runs long, Threads and Timeline can be descoped to "Should Have." The product works with just Document + Decisions + AI synthesis. |
| R7 | **OpenRouter dependency** — service outage blocks synthesis | Low | Medium | Graceful degradation: Gist is fully readable without synthesis. Error message in Synthesis Panel. No content is ever blocked by AI failure. |

## 12. Launch Plan

### Phase 0: Dogfood

- **Who:** Narain, using Gist across 2+ real client/advisory engagements
- **Duration:** 2-4 weeks minimum
- **Success criteria:** The Gist becomes where people go to get up to speed — not because they're told to, but because it's faster and better than the alternative
- **Invalidation signal:** Users create Gists but collaborators don't engage. Or AI synthesis is too slow/shallow. Or the author maintains parallel records despite having the Gist.

### Phase 1: Small Cohort

- **Who:** 5-10 practitioners in the same space (fractional execs, senior consultants). Invite-only.
- **Trigger:** Phase 0 validates — Gist is genuinely the best place to get context
- **Success criteria:** 50 cross-org active Gists. Users report the collaborator aha ("I'm caught up").
- **Duration:** 4-8 weeks

### Phase 2: Public Release

- **Trigger:** Phase 1 metrics met. Pricing validated. Product stable.
- **Domain:** gist.works
- **Rollback plan:** If metrics collapse post-public, revert to invite-only and investigate. The file-over-app architecture means no data is ever lost — every Gist is a .md file the user owns.
